## Почему стоит использовать Next? (Ключевые особенности Next.js)
 - Гибкий рендеринг (SSR, SSG, ISR, CSR) Next.js поддерживает различные методы рендеринга:
     - SSR (Server-Side Rendering): Это рендеринг на сервере, при котором HTML страницы генерируются на сервере при каждом запросе. Это помогает улучшить SEO и время первой загрузки.

     - SSG (Static Site Generation): Генерация статических страниц на этапе сборки, что ускоряет загрузку сайта, поскольку страницы уже сгенерированы и готовы для отправки.

     - ISR (Incremental Static Regeneration): Позволяет обновлять только те страницы, которые были изменены, без необходимости пересборки всего сайта, что делает сайт более динамичным и быстрым.

     - CSR (Client-Side Rendering): Стандартный рендеринг на клиенте, когда React полностью загружает и рендерит приложение на клиентской стороне.

 - SEO-оптимизация
     - Так как Next.js поддерживает SSR и SSG, это улучшает индексацию страниц поисковыми системами. В отличие от обычных одностраничных приложений (SPA), где контент часто рендерится на клиенте и может быть трудным для поисковых систем для индексации, серверный рендеринг позволяет отдавать готовые страницы с данными, что улучшает SEO.

 - API маршруты
     - Next.js позволяет создавать серверные API-эндпоинты в рамках самого проекта, без необходимости использования внешнего бекенд-сервера. API-функции размещаются в папке pages/api/, и могут быть использованы для обработки запросов, работы с базой данных или взаимодействия с внешними сервисами.

 - Поддержка PWA (Progressive Web App)
     - Next.js позволяет легко превращать приложение в PWA, что помогает улучшить пользовательский опыт, предоставляя возможности для работы в оффлайн-режиме, кэширования данных и улучшенной производительности.

 - Мобильная оптимизация и адаптивность
     - Next.js предоставляет инструменты для адаптации приложения под мобильные устройства, включая автоматическую оптимизацию изображений и поддержку различных типов рендеринга. Это помогает создавать быстрые и адаптивные мобильные приложения.

Дополнительные плюсы **+** :
 - Автоматическая оптимизация шрифтов и изображений.
 - Расширенный fetch c поддержкой кэширования.
 - Поддержка предпочитаемых методов стилизации, включая модули CSS, Tailwind CSS и CSS-in-JS.

# 2. Гибкий рендеринг (SSR, SSG, ISR, CSR)

## SSR (Server-Side Rendering)

**SSR** позволяет генерировать HTML на сервере при каждом запросе, что гарантирует, что пользователи всегда получают актуальную информацию.

 - Как работает SSR:
     - Сервер генерирует страницу для каждого запроса.

     - Все данные загружаются и рендерятся на сервере.

     - HTML-страница отправляется пользователю, и она готова к отображению.

 - Когда использовать SSR?

     - Когда данные часто меняются и должны быть актуальными при каждом запросе.

     - Например, для страниц с часто обновляющимся контентом, таких как новости или динамические поисковые результаты.

### Пример:

```javascript
"use server"
        // pages/products.js
        export async function getServerSideProps() {
        const res = await fetch('https://api.example.com/products');
        const products = await res.json();

        return {
            props: { products }, // передаем данные в компонент
        };
        }

        export default function Products({ products }) {
        return (
            <div>
            <h1>Список продуктов</h1>
            <ul>
                {products.map(product => (
                <li key={product.id}>{product.name}</li>
                ))}
            </ul>
            </div>
        );
        }

```
 - **getServerSideProps** — это асинхронная функция, которая выполняется на сервере при каждом запросе. Она загружает данные и передает их в компонент.

## SSG (Static Site Generation)
**SSG** позволяет генерировать HTML на этапе сборки (build-time), а не при каждом запросе. Это полезно, если контент страницы не изменяется часто.

 - Как работает SSG:
Страница генерируется во время сборки.

     - HTML-контент предгенерируется и хранится в виде статических файлов.

     - Страницы быстро загружаются, так как они уже сгенерированы.

 - Когда использовать SSG?

     - Статические страницы, которые не требуют частого обновления.

     - Например, блоги, документация, маркетинговые страницы.
    
### Пример:

```javascript
"use server"
// pages/blog.js
export async function getStaticProps() {
  const res = await fetch('https://api.example.com/blogs');
  const blogs = await res.json();

  return {
    props: { blogs }, // передаем данные в компонент
  };
}

export default function Blog({ blogs }) {
  return (
    <div>
      <h1>Список блогов</h1>
      <ul>
        {blogs.map(blog => (
          <li key={blog.id}>{blog.title}</li>
        ))}
      </ul>
    </div>
  );
}
```
 - **getStaticProps** — выполняется во время сборки (build-time) и позволяет получить данные для страницы, которые затем будут сгенерированы как статический HTML.

## ISR (Incremental Static Regeneration)
**ISR** позволяет обновлять статические страницы на лету после сборки, не перезапуская весь процесс сборки. Это позволяет генерировать страницы статически и обновлять их через заданные интервалы времени.

 - Как работает ISR:
     - Статическая страница генерируется при сборке.

     - По истечении времени TTL (Time-To-Live) страница будет заново сгенерирована при следующем запросе.

ISR помогает поддерживать актуальность контента, при этом не теряя преимуществ статического рендеринга.

 - Когда использовать ISR?

     - Когда контент обновляется не слишком часто, но нужно обновить страницу без повторной сборки всего сайта.

     - Например, для страниц с результатами поиска, новостей или отчетов.

### Пример:

```javascript
"use server"
// pages/products.js
export async function getStaticProps() {
  const res = await fetch('https://api.example.com/products');
  const products = await res.json();

  return {
    props: { products },
    revalidate: 10, // Перегенерировать страницу каждые 10 секунд, именно этот параметр позволяет создать ISR - за счет инвалидации кеша
  };
}

export default function Products({ products }) {
  return (
    <div>
      <h1>Список продуктов</h1>
      <ul>
        {products.map(product => (
          <li key={product.id}>{product.name}</li>
        ))}
      </ul>
    </div>
  );
}
```
 - **revalidate в getStaticProps** — указывает интервал времени, через который страница будет перегенерирована.

> Также есть функция **getStaticPaths** - Эта функция используется в сочетании с **getStaticProps** для динамической генерации путей для статических страниц. Когда у вас есть динамические маршруты, например, страницы с параметрами в URL (например, /product/[id]), Next.js использует **getStaticPaths**, чтобы определить, какие динамические страницы должны быть сгенерированы на этапе сборки.

### Когда используется?

 - Когда у вас есть динамические маршруты, например, страницы с параметрами (например, /post/[id]), и вы хотите заранее сгенерировать только определенные страницы во время сборки.

 - Если у вас много таких динамических маршрутов, то можно использовать getStaticPaths, чтобы указать, какие страницы нужно заранее сгенерировать, а остальные можно генерировать на лету.

### Как работает?

 - getStaticPaths возвращает массив путей, которые должны быть сгенерированы на этапе сборки.

 - Для каждого пути будет вызываться getStaticProps, чтобы сгенерировать страницу с необходимыми данными.

```javascript
// pages/product/[id].js
export async function getStaticPaths() {
  // Получаем список всех продуктов для генерации путей
  const res = await fetch('https://api.example.com/products');
  const products = await res.json();

  // Создаем массив путей для каждой страницы продукта
  const paths = products.map((product) => ({
    params: { id: product.id.toString() }, // Параметр id для динамического маршрута
  }));

  return {
    paths, // передаем массив путей
    fallback: false, // если страницы нет в списке paths, вернется 404
  };
}

export async function getStaticProps({ params }) {
  const { id } = params;
  const res = await fetch(`https://api.example.com/products/${id}`);
  const product = await res.json();

  return {
    props: { product },
  };
}

export default function ProductPage({ product }) {
  return (
    <div>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
    </div>
  );
}
```

## Ограничения для использования серверных компонентов

В серверных компонентах (Использующих директиву "use server") есть ряд ограничений :
- Ограничения на использование состояния и хуков (Такие как useState)
    - Ограниченная совместимость с JavaScript библиотеками, требующими состояния
- Не поддерживаются браузерные API (Такие как DOM, addEventListener)
- Нет поддержки клиентских библиотек
- Невозможность использовать клиентский роутинг внутри серверных компонентов


В следствии таких ограничений:
 - Серверные компоненты могут включать в себя клиентские
 - Клиентские не могут включать в себя серверные


# Next как основа для PWA

Next.js делает процесс превращения приложения в PWA (Progressive Web App) достаточно простым благодаря использованию встроенных возможностей и пакетов, таких как **next-pwa**.
Пакет **next-pwa** автоматически генерирует сервис-воркер и настраивает кэширование в вашем приложении на **Next.js**. Он использует стратегию кэширования для оптимизации загрузки ресурсов и работы в оффлайн-режиме

> В файле конфигурации **next.config.js** нужно добавить настройки для next-pwa.

Для **PWA** необходимо создать файл манифеста, который содержит метаданные вашего приложения, такие как имя, иконки и другие параметры. Этот файл обычно называется **manifest.json** и размещается в папке **public**

# 3. Гидратация

**Гидратация** — это процесс, при котором клиентская сторона выполняет код JavaScript, чтобы "восстановить" состояние, добавленное сервером, и сделать страницу интерактивной. Таким образом, страница, сгенерированная на сервере, становится динамичной, и JavaScript начинает управлять поведением UI (например, обновлением состояния или обработкой событий).

Когда сервер рендерит страницу, он генерирует HTML, который включает в себя разметку (markup) и, возможно, некоторые инлайновые данные (например, данные о пользователе, переданные с сервером). Однако этот HTML не имеет интерактивности, пока JavaScript не "гидратирует" его на клиенте.

 - Шаг 1: Рендеринг на сервере — Сервер создает HTML-страницу (SSR).

 - Шаг 2: Отправка на клиент — Клиент получает этот HTML-код.

 - Шаг 3: Гидратация — Когда JavaScript запускается на клиенте, React (или другой фреймворк) "гидратирует" статическую HTML-страницу, прикрепляя обработчики событий, обновляя состояние и предоставляя возможность взаимодействия.

## Проблемы гидратации
Несоответствие серверного и клиентского рендеринга
Гидратация может вызвать проблемы, если HTML, сгенерированный на сервере, не совпадает с тем, что генерируется на клиенте, в том числе:

 - Несоответствие контента: Например, если на сервере рендерится что-то одно (например, текст в параграфе), а на клиенте из-за каких-то изменений (например, состояния компонента или асинхронных данных) результат отличается, это приведет к ошибке гидратации.

 - Ошибки в инициализации состояния: Если в компоненте используется состояние, которое изменяется после рендеринга, а это состояние влияет на структуру или содержимое HTML, это может привести к разнице между серверным и клиентским HTML.

Чтобы избежать таких ошибок, важно:

 - Соблюдать синхронность между сервером и клиентом.

 - Использовать подходы, как getServerSideProps и getStaticProps в Next.js, чтобы гарантировать, что данные, необходимые для рендеринга, доступны и на сервере, и на клиенте.


# 4. Кеширование

**Кеширование в Next.js** — это важная часть оптимизации производительности веб-приложений. Оно помогает уменьшить нагрузку на сервер и ускорить время отклика, хранит часто запрашиваемые данные и страницы и возвращает их без необходимости повторного выполнения сложных вычислений. В Next.js кеширование можно разделить на несколько уровней, каждый из которых отвечает за разные аспекты оптимизации.

Есть 4 уровня кеширования в Next:
 - Кеширование на уровне страницы (Page Caching)
     - Это кеширование целых HTML-страниц, которые генерируются сервером. При запросе страницы сервер сначала проверяет, есть ли уже сгенерированная версия этой страницы в кеше, и если есть, сразу возвращает её без повторной генерации.
 - Кеширование данных (Data Caching)
     - На этом уровне кешируются результаты API-запросов или данных, которые могут часто изменяться, но часто запрашиваются на сервере. Используются кеширующие механизмы для хранения этих данных, чтобы не запрашивать их с базы данных или других источников каждый раз.
 - Кеширование на уровне CDN (Content Delivery Network)
 - Кеширование на уровне клиента (Client-side Caching)
     - Это кеширование на стороне клиента, где браузер сохраняет ресурсы и данные в кеш для ускорения загрузки страниц при последующих посещениях.


Данные о страницах могут быть закешировоаны на нескольких слоях:
 - 1. На клиенте (Кэш маршрутизатора на стороне клиента) (клиент)
 - 2. Полный кеш маршрута (сервер)
 - 3. Запоминание запросов (сервер)
 - 4. Кеш данных (сервер)

### **1. На клиенте (Кэш маршрутизатора)**
Этот уровень определяет кеширование на стороне клиента(браузера)

### **2. Полный кеш маршрута**
Next. js автоматически отображает и кэширует маршруты во время сборки. Это оптимизация, которая позволяет использовать кэшированный маршрут вместо рендеринга на сервере для каждого запроса, что ускоряет загрузку страниц.

Каждый фрагмент визуализируется в два этапа:

 - React преобразует серверные компоненты в специальный формат данных, оптимизированный для потоковой передачи, который называется полезной нагрузкой(RSC) серверного компонента React.
 - Next.js использует инструкции JavaScript для серверных и клиентских компонентов React для рендеринга HTML на сервере.

По умолчанию Next кэширует отображаемый результат (полезную нагрузку серверного компонента React и HTML) маршрута на сервере

### **3. Запоминание запросов**
Next.js расширяет fetchAPI для автоматической запоминания запросов с одинаковым URL-адресом и параметрами. Это означает, что вы можете вызывать функцию выборки для одних и тех же данных в нескольких местах в дереве компонентов React, выполняя её только один раз.
> Кеш живет до тех пор пока монтируется новое дерево Реакт элементов, после чего очищается

>Кэширование применяется только к методу GET в запросах fetch, другие методы, такие как POST и DELETE, не кэшируются.

> Функция кеширования запросов - принадлежит не Next, а React!

***Жизенный цикл кеширования запросов***
 - При первом вызове конкретного запроса при рендеринге маршрута его результат не будет находиться в памяти и будет кэшироваться MISS.
 - Таким образом, функция будет выполнена, данные будут получены из внешнего источника, а результат будет сохранён в памяти.
 - Последующие вызовы функции запроса в том же проходе рендеринга будут кэшироваться HIT, и данные будут возвращаться из памяти без выполнения функции.
 - После рендеринга маршрута и завершения рендеринга память «очищается», и все записи кэширования запросов удаляются.

### **4. Кеш данных**
В Next.js есть встроенный кэш данных, который сохраняет результаты выборки данных при поступлении запросов с сервера и развертывании. Это возможно благодаря тому, что Next.js расширяет собственный fetch API, позволяя каждому запросу на сервере устанавливать собственные параметры постоянного кэширования.
>Кэш данных сохраняется при поступлении новых запросов и развёртывании, если вы не отмените его или не откажетесь от него.

> Функция кеширования данных - уже принадлежит Next!

***Жизенный цикл кеширования данных***
 - При первом вызове запроса fetch с опцией 'force-cache' во время рендеринга Next.js проверяет кэш данных на наличие кэшированного ответа.
 - Если найден кэшированный ответ, он возвращается немедленно и сохраняется в памяти.
 - Если кэшированный ответ не найден, запрос отправляется к источнику данных, результат сохраняется в кэше данных и запоминается.
 - Для не кэшируемых данных (например, без опции cache или с использованием { cache: 'no-store' }), результат всегда извлекается из источника данных и запоминается.
 - Независимо от того, кэшируются данные или нет, запросы всегда сохраняются в памяти, чтобы избежать дублирования запросов к одним и тем же данным во время рендеринга React.

> Полезно знать: В браузере cache опция fetch указывает, как запрос будет взаимодействовать с HTTP-кэшем браузера, в Next.js , параметр cache указывает, как запрос на стороне сервера будет взаимодействовать с кэшем данных сервера.


```js
export async function getServerSideProps(context) {
  const data = await fetch('someUrl', { 
    cache: 'no-cache' | 'force-cache', // ОПРЕДЕЛЕНИЕ КЕШИРОВАНИЯ НА УРОВНЕ 3 - ЗАПРОСОВ
    next: { 
        revalidate: 3600,
        tags: ['a'] // прикрепляет теги для инвалидации
        } // ОПРЕДЕЛЕНИЕ КЕШИРОВАНИЯ НА УРОВНЕ 4 - КЕШ ДАННЫХ (ДЛЯ SSR)
    });

    // ИЛИ
    context.res.setHeader('Cache-Control', 'public, max-age=60, s-maxage=60, stale-while-revalidate=30');

  return { 
    props: { data },
  };
}

export async function getStaticProps() {
  const data = await fetch('someUrl');
  return { 
    props: { data }, 
    revalidate: 10 // ОПРЕДЕЛЕНИЕ КЕШИРОВАНИЯ НА УРОВНЕ 4 - КЕШ ДАННЫХ (ДЛЯ SSG)
    };
}

revalidatePath('/') // Функции для инвалидации кеша по урлу
revalidateTag('a') // Функции для инвалидации кеша по тегу
```

Для кеширования на стороне клиента можно использовать такие инструменты, как **Service Workers** или сторонние библиотеки (Например **swr**)
