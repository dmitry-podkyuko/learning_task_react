# Информация о Микрофронтах

## Что такое микрофронты?

Это подход к разработке приложения, который разбивает одно монолитное приложение на несколько приложений поменьше, которые работают независимо и подключаются в главное приложение.

## Как это работает?

Есть HOST-приложение, которое доступно пользователю, и есть REMOTE-приложение, которое встраивается в HOST.

На схеме есть HOST-приложение и 8 REMOTE-приложений, которые встраиваются в основное приложение. В данном случае все приложения работают независимо друг от друга. Эта схема подойдет для приложения, сочетающего в себе абсолютно независимые части, которые можно запустить отдельно друг от друга. Например, приложение может включать в себя видеозвонки, чат и базу знаний, но также эти части могут использоваться автономно (хранят в себе достаточно логики для работы - это может быть и свой собственный стор, собственный UI-kit, собственное API и прочее).

При этом они используют одно DOM дерево, одни наименования (классов, ID и пр.) для стилизации.


## Как работает HOST приложение?
HOST - это приложение, которое делает запрос к другим приложениям и встраивает их в себя. Но при этом встраивает дерево реакт элементов(ДРЭ) удаленного приложения в свое ДРЭ.
> !ВАЖНО: Встраивание происходит НЕ посредством iframe, а именно ДРЭ.

## Как работает REMOTE приложение?
REMOTE - это обычное веб-приложение, которое доступно в сети интернет. У него есть свой собственный бандл, который подключается в свой index.html
Но помимо бандла там создается еще 1 файл - так называемый remote файл, который хранит информацию о том как обращаться из HOST приложения к компонентам бандла. Именно к remote файлу идет обращение извне.


REMOTE приложение также может выступать в роли HOST приложения для других приложений.

## Плюсы микрофронтов

1. **Модульность**: Позволяет разбивать приложение на независимые части, что упрощает разработку и поддержку.
2. **Независимость разработки**: Разные команды могут работать над разными микрофронтами одновременно, не мешая друг другу.
3. **Гибкость технологий**: Возможность использовать разные технологии и фреймворки для разных частей приложения.
4. **Масштабируемость**: Легче масштабировать отдельные части приложения в зависимости от нагрузки.
5. **Обновления и развертывание**: Обновления могут быть развернуты для отдельных микрофронтов без необходимости обновления всего приложения.
6. **Повторное использование**: Микрофронты могут быть использованы в разных проектах, что повышает эффективность разработки.
7. **Возможность использовать одни зависимости**: Во всех микрофронтах могут использоваться одинаковые библиотеки. Микрофронт архитектура позволяет добавить в банд только 1 версию какой-либо зависимости и использовать ее во всех REMOTE приложениях.

## Минусы микрофронтов

1. **Сложность интеграции**: Требуется продуманная архитектура для интеграции разных микрофронтов в единое приложение.
2. **Управление состоянием**: Сложнее управлять общим состоянием приложения, когда оно разбито на несколько частей.
3. **Повышенные требования к инфраструктуре**: Необходимость в более сложной инфраструктуре для развертывания и управления микрофронтами.
4. **Перекрестные зависимости**: Возможны проблемы с зависимостями между микрофронтами, что может усложнить их обновление.
5. **Производительность**: Возможны накладные расходы на загрузку и инициализацию нескольких микрофронтов.
6. **Безопасность**: Увеличивается поверхность атаки, так как каждое приложение может иметь свои уязвимости.

Микрофронты предоставляют значительные преимущества в гибкости и масштабируемости, но требуют тщательного планирования и управления для успешной реализации.

## Создание микрофронтенд архитектуры

Для настройки микрофронтов можно использовать различные сборщики и инструменты, такие как:

1. **Webpack**: Популярный инструмент для сборки JavaScript приложений. Поддерживает микрофронты через модули и динамическую загрузку. Для создания микрофронтовой архитектуры используется **Webpack Module Federation**.
2. **Vite**: Быстрый сборщик, который поддерживает микрофронты и обеспечивает быструю разработку благодаря использованию ES-модулей. Для создания микрофронтовой архитектуры используется **Vite Module Federation**.
3. **Single-SPA**: Фреймворк для создания микрофронтов, который позволяет интегрировать разные фреймворки и библиотеки в одно приложение.

Эти инструменты позволяют эффективно управлять микрофронтами, обеспечивая модульность и гибкость в разработке.

## Пример создания микрофронтов на Webpack

### **HOST**

```javascript
module.exports = {
    ...baseConfigWebpack,
    plugins: [
        ...baseConfigWebpack.plugins,
new ModuleFederationPlugin({
                name: "HOST",
                filename: "common.js",
                remotes: {
                    TASKER_IN_HOST: "TASKER@http://localhost:6051/remote_1.js",
                    // TASKER_IN_HOST - Имя по которому идет обращение внутри HOST приложения
                    // TASKER - Имя которое назначено внутри сборщика REMOTE 
                    // http://localhost:6051/remote_1.js - путь, по которому следует обратится для получения файла REMOTE приложения
                    CHAT: "CHAT@http://localhost:6052/remote_2.js"
                },
                shared: {
                    react: { 
                        singleton: true, // Определяется, что зависимость будет общая
                        requiredVersion: '~19.0.0', // Указывается версия зависимости
                        eager: true // Указывает, что общий модуль должен быть загружен немедленно, а не по требованию.
                    },
                    "react-dom": {
                        singleton: true,
                        requiredVersion: '~19.0.0',
                        eager: true
                    }
                } // shared - говорит какие библиотеки общие между всеми микрофронтами.
            }),
    ],
}
```

### **REMOTE**

```javascript
module.exports = {
    ...baseConfigWebpack,
    plugins: [
        ...baseConfigWebpack.plugins,
new ModuleFederationPlugin({
                name: "TASKER",
                // TASKER - Имя которое будет доступно обращение
                filename: "remote_1.js",
                // Файл для обращения извне
                exposes: {
                    "./App": "./src/tasker.tsx" 
                    // Имя и путь к файлу, которые будет получать HOST приложение
                    // App - имя компонента (как к нему обратится) 
                },
                // Доступные микрофронты для обращения
                shared: {
                    react: { 
                        singleton: true,
                        requiredVersion: '~19.0.0',
                        eager: true
                    },
                    "react-dom": {
                        singleton: true,
                        requiredVersion: '~19.0.0',
                        eager: true
                    }
                }
            }),
    ],
}
```

> **Важно**: Поля в `shared` должны быть идентичны между REMOTE и HOST приложениями.

**Для обращения к компоненту микрофронта из HOST приложения**

```javascript
import { lazy, Suspense } from "react";

const Remote = lazy(() => import('TASKER_IN_HOST/App'));

export const Tasker = () => {
    const remoteProps = { ...any_data };
    return (
        <Suspense fallback={() => <>Loading</>}>
            <Remote {...remoteProps}/>
        </Suspense>
    );
}
```
